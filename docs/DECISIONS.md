# DECISIONS.md — Quicklo

> **What this file is.** A single, append-only log of every *locked* decision and every *changed* decision. One entry per decision. Newest at the top.
>
> **When an entry is added.** Any time a choice is made that future-you (or Claude, or Claude Code) would otherwise have to re-derive, second-guess, or could accidentally contradict. If it has a *reason*, it belongs here. Routine work that simply follows existing rules does **not** belong here.
>
> **The three-month test.** If three-months-from-now Marko would be confused, would redo work, or would ask "why did we do it this way?" without this line — log it.
>
> **Format.** `YYYY-MM-DD — [AREA] short statement. Why: reason. Touched: which docs/files were updated.`
> Areas: `BRAND` · `COLOUR` · `TYPE` · `STACK` · `ARCH` · `DESIGN-SYSTEM` · `PRODUCT` · `SECURITY` · `PROCESS` · `PRICING`
>
> **Never delete an entry.** If a decision is reversed, add a NEW entry that supersedes it and note "Supersedes 20XX-XX-XX".

Polaris' `ResourceList`-vs-`DataTable` boundary, and specifically its "don't swap markup to a list for the condensed view" lesson, informed the CSS-only responsive approach — the same `<table>` DOM restyles into a card stack below 768px via CSS alone, never a `<ul>` swap. WCAG 2.5.8 (Target Size, AA, 24px) vs 2.5.5 (Target Size, AAA, 44px), plus Housecall Pro's own large-tap-target mobile pattern, informed keeping every interactive control (row checkbox, sort header, action buttons) at this system's locked 44×44px floor even inside the denser desktop table row, rather than accepting the lower AA bar.

**Five confirmed decisions.** (1) The 768px (`md`) table↔card flip point, matching this system's existing `md` breakpoint semantics (side panels) rather than introducing a Table-specific breakpoint. (2) Single 48px density with automatic ~64px auto-grow for a two-line `primary` cell; `compact` 40px explicitly deferred. (3) `ChevronsUpDown` (new icon) for the neutral/unsorted sort affordance, `ChevronDown` reused (rotated 180° for ascending) for the active state — the same rotate-on-state technique `Select`'s own chevron already uses, not a new pattern. **A real bug was caught and fixed via live Playwright verification, not shipped.** The selection checkbox column and a `hideBelow:'md'` column both remained visible at 390px despite being marked `hidden md:table-cell` (Tailwind classes). Root cause: `.quicklo-table-cell`'s own `display:flex` declaration (in Table's injected `<style>` block, rendered inside the React tree) and Tailwind's `.hidden{display:none}` utility (compiled into a `<head>` stylesheet, earlier in document order) are both single-class selectors of equal specificity — and because Table's own stylesheet renders LATER in the DOM, it silently wins ties over Tailwind's utility, the identical mechanism Tabs' and Badge's own injected `<style>` blocks rely on to override Tailwind (see those components' own DECISIONS entries) — except here it worked AGAINST the intended visibility instead of for it. Fixed by moving the hide logic into two dedicated modifier classes declared in Table's own stylesheet (`.quicklo-table-cell--select`/`--hide-mobile`), so there is no cross-stylesheet specificity race left to lose. Confirmed fixed live: at 390px the checkbox column and the `hideBelow` column are both genuinely absent, not just visually clipped.

Rather than ship a component that fires a console warning on every default Table error, or modify Alert's own locked constraint to accommodate one caller, Table's default error content omits the icon override and accepts Alert's native `XCircle` for the error tone. `errorContent` remains fully overridable per-instance for a consumer who wants a different treatment.

**Readout is custom, touch-first — SUPERSEDES the draft "reuses the Tooltip component" line.** `src/components/ui/Tooltip` is hover/focus-only and never fires on tap, unusable for this product's mobile-first, one-handed usage pattern. Built instead: `activeIndex` plain React state, set via pointer-position math computed directly from the pointer/click event — deliberately NOT Recharts' own internal `activeTooltipIndex`/mousemove wiring, which is inconsistent across touch browsers. This is the same "robust math over library/DOM-measurement fragility" preference already applied to Tabs' sliding-pill index math and Pagination's CSS-breakpoint responsive collapse instead of measuring. Plus `--color-chart-grid`/`-axis`/`-track` (structural/decorative) and `--color-chart-readout-bg`/`-text` (the readout pill). The `-muted`/`-fill-*` tokens are `color-mix()` derivations, declared in BOTH `:root` and `.dark` — the same Badge/Alert/Avatar baking rule (a `color-mix()` custom property bakes in its `var()` inputs at its declaring selector and does not re-substitute per descendant; a `:root`-only declaration would freeze dark mode at the light-mode mix).

**Accesslint / WCAG 1.4.11 audit (Node relative-luminance script, ≥3:1 required for graphical fills, checked against `--color-bg-surface` in both modes) — full table in `docs/DOC-colour-system.md`.** Result: `chart-primary` and `cat-1..5` ALL PASS as specified (light 5.02–18.73:1, dark 6.01–12.27:1) — `yellow-700` (`cat-4`) and the grey stops (`cat-2`/`cat-5`), flagged in the build brief as the likely risks, actually clear 3:1 with real margin; **no stop substitution was needed anywhere**. `chart-primary-muted` is the one deliberate, DOCUMENTED exception: it measures 1.39:1 light / 1.53:1 dark, both well under 3:1 — but this token exists specifically to render a de-emphasized ghost/comparison fill (muted bars, the prior-period dashed line) that must never compete with the primary per the component's own brief; reaching 3:1 would require a 68%/54% mix, visually near-indistinguishable from the full-strength primary, defeating the token's purpose. WCAG 1.4.11 exempts graphical objects not required to understand the content — the muted fill is always supplementary, never the sole carrier of a value, and the component's own sr-only data-table mirror plus direct value labels keep every number accessible regardless of this fill's contrast. Kept at 22% mix, not substituted.

**Accessibility architecture — role="img" wraps ONLY the visual plot.** Each variant's own root renders `role="img"` `aria-label` around the Recharts plot alone, never around a legend or the readout pill — `role="img"` prunes descendants from the accessibility tree, so anything meant to stay independently reachable (an interactive legend toggle, the pill's `aria-live` region) has to sit outside it as a sibling. A visually-hidden (`sr-only`) `<table>` mirrors the underlying data as a further sibling, per WCAG dataviz guidance that a hover/tap readout is never sufficient alone — skipped only for `sparkline` (bare embed, no independent accessible identity beyond its surrounding `MetricCard`). For radial/donut, the big centre value sits INSIDE the pruned `role="img"` subtree, so `ariaLabel` must be a complete description including the value (e.g. "Response rate: 62 percent") — documented in the component's own JSDoc and in CLAUDE.md.

**`ChartEmptyState` is a local stand-in, not the real `EmptyState` component.** `EmptyState` is on the Approved list but unbuilt (same situation `Modal`/`Card` were in when `DateTimePicker`/`Pagination` needed them) — a local, folder-scoped implementation (icon + payoff copy) was built instead, flagged for migration once the real component ships, the same precedent `DateTimePicker`'s overlay set for `Modal`.

Why: Marko's brief specified this exact shape — 6 variants, Option A palette, a custom readout, the accessibility architecture above — this entry records the research/verification behind it (the accesslint audit results, the role=img architecture reasoning, the Tooltip/readout decision) so it isn't re-derived or second-guessed later.

**Four variants, and why each earns its place.** `numbered` — the classic page-number row + prev/next + ellipsis truncation, desktop/table-oriented, for jumping directly to an arbitrary page of a bounded dataset (the admin dashboard's data tables). `prev-next` — compact, labelled-or-icon-only prev/next plus a short context readout; the mobile-safe default, since it has no page-count-dependent width and no ellipsis math to collapse. `table` — a full data-table footer bar (optional rows-per-page `Select` · numbered/prev-next · range readout), spanning the table's width with a 1px `--color-border-default` top divider so it sits flush under the table body, no gap (Carbon's own data-table-footer convention — "stacked below, no padding between"). `load-more` — a single full-width "Load more" `Button` + an optional "Showing X of Y" readout, swapping to a quiet "You're all caught up" line once `hasMore` is false.

This is judged sufficient because colour was never meant to be the sole state signal for this component (the pre-existing build already treated colour-plus-something-else as the rule, e.g. `active/selected`'s indicator + colour on `line`), and a raised, shadowed surface is itself a strong, unambiguous "this one is selected" signal independent of any text colour.

**Implementation — a small injected `<style>` block, not stacked Tailwind variants, and why.** The per-mode label fallback is written in `Tabs.jsx` as a scoped `<style>` tag (`.quicklo-segmented-trigger` class, rendered once per segmented `Tabs.List`) rather than combinations of Tailwind's `dark:` and `data-[state=active]:` utility variants. Reason: those two variants have no documented precedence relative to each other in this project's Tailwind configuration when they'd otherwise conflict (unselected-dark wants `--color-text-secondary`, active wants `--color-text-primary` — both single-variant utilities of equal specificity), and getting that override backwards would be a silent, easy-to-miss contrast regression, not an obviously-wrong visual bug someone would immediately flag in review. Writing the three rules directly as plain CSS (base, `.dark` unselected override, hover override) makes the cascade order explicit and deterministic instead of dependent on framework-internal utility-ordering behaviour. This mirrors Badge's own existing use of an injected `<style>` tag for its pulse-animation keyframes — the same "inject scoped CSS for something Tailwind's utility classes can't cleanly express" pattern, not a new technique for this codebase.

**Selected-pill motion — a sliding layer, gated on `fitted`, computed via index math.** In `fitted` mode (the default — equal-width segments), the selected pill now slides between segments: a single absolutely-positioned `<div>` inside `Tabs.List`, width equal to one segment (`calc((100% - 2 * var(--space-1)) / N)`), `transform: translateX(selectedIndex * 100%)`, transitioning on `--duration-base`/`--ease-default`. `selectedIndex` is derived from `React.Children.toArray(children)` — the ordered list of the List's child `Tabs.Trigger` `value` props, matched against the active value from context — at render time. This is explicitly NOT a DOM measurement and NOT a `ResizeObserver`: it's arithmetic over props, valid specifically because `fitted` segments are equal-width by construction (`flex: 1 1 0%`), so "where is segment N" reduces to `N * 100%` rather than something that needs measuring. This is the same fragility class this component has deliberately avoided everywhere else (`line`'s cross-fade-not-sliding-indicator, the Overflow section's static-not-measured edge-fade mask — both from the original Tabs build, see the entry below).

`fitted={false}` (a genuinely content-width/scrollable set) skips the sliding layer entirely and falls back to giving the selected segment its own direct `--color-bg-surface`/`--elevation-1` background — there is no shared equal-width layer to slide against in that case. **One accepted, explicitly-flagged edge case:** a `fitted={true}` (the default) segment set that ALSO happens to overflow its container invokes the pre-existing, separate flexbox auto-degrade-to-content-width behaviour (unequal segment widths), which the sliding pill's equal-division math doesn't know about — the pill's assumed width could misalign against actually-unequal segments in that specific scenario. Rather than add measurement to detect this (which would violate the explicit "no DOM measurement" requirement), the Storybook Overflow demo — which is inherently this exact scenario, 6 segments in a 280px container — was updated to pass `fitted={false}` explicitly, since it always was a content-width/scrollable demonstration and never truly an equal-width one; this resolves the ambiguity at the call site rather than needing runtime overflow detection in the component.

**States: `resting`/`entering`/`exiting` only, entering/exiting gated behind `dismissible`.** A non-dismissible Alert never enters a state machine at all — `status` starts and stays `'resting'`, and the component skips the animation-wrapper divs entirely (returns the plain alert box), since there's nothing to animate: it exists because the consumer renders it, and disappears because the consumer stops. A dismissible Alert starts at `'entering'` (collapsed + transparent) and flips to `'resting'` one animation frame later via `requestAnimationFrame` — identical two-step promotion technique to `ToastProvider`'s `queued → entering → resting` — so mounting a dismissible Alert gets a brief pop-in rather than an abrupt appearance, symmetric with the exit. Exit: clicking close sets `'exiting'`, waits `--duration-base` (read live via `getComputedStyle`, same convention as Toast/DateTimePicker — never hardcoded), then sets `'dismissed'` (Alert renders `null` from that point, self-removing regardless of whether the consumer's own state also changes) and calls `onDismiss?.()`. The fade+collapse itself is CSS-only — a `grid-template-rows: 1fr ↔ 0fr` transition wrapping an `overflow:hidden` div wrapping an opacity-transitioned div — deliberately NOT a JS-measured max-height animation: `grid-template-rows` animates cleanly to/from intrinsic content height with zero measurement code, and content below the alert reflows automatically as the row collapses, exactly the requirement in the brief. `--ease-spring` was NOT used (that curve stays locked to toggles/checkboxes/status-dots per the Motion tokens rule) — `--ease-enter`/`--ease-exit` throughout, matching Toast. Excluded states, mirroring Toast's own exclusion list: no `hover` (container isn't interactive), no `disabled` (shown or not, no partial-interactivity concept), no `loading` (async lives on the composed `Button`), no "error as a state" (error is a tone, not a state transitioned into). Read/unread belongs to the future `NotificationItem` pattern, not here.

**Accessibility.** ARIA split identical in shape to Toast: `warning`/`error` → `role="alert"` `aria-live="assertive"`; `info`/`success` → `role="status"` `aria-live="polite"`. Title is the accessible name; `hideTitle` sr-only-hides it while keeping it in the DOM, dev-warned if `aria-label` is absent (matches the Input/Select/DateTimePicker `hideLabel` convention exactly); a separate dev warning fires if NEITHER `title` NOR `aria-label` is supplied at all. Alert never auto-moves focus on mount — the brief explicitly reserved that behaviour for a future form-error-summary use case, and implementing it speculatively here (e.g. "focus the alert when tone=error") would be exactly the kind of unrequested scope this project's rules warn against, and would actively hurt a page with more than one standing alert (whichever renders last would keep stealing focus). `React.forwardRef` reaches the actual alert `<div>` regardless of how many animation-wrapper divs a dismissible instance renders inside — `ref` is attached directly to the semantic element, not the wrapper. `{...rest}` is spread BEFORE the component's own `role`/`aria-live`/`className`/`style` in JSX prop order (not after) — a deliberate ordering choice, not an oversight: JSX's "last prop wins" rule means spreading `{...rest}` last would let a stray or accidental prop (e.g. a consumer passing `style` for an unrelated tweak) silently clobber Alert's computed ARIA role/live-region or its token-driven colours. This is a correctness detail worth stating explicitly because it is easy to get backwards.

**Colours are set via inline `style` with the tone interpolated into the CSS custom property name (`` `var(--color-alert-${tone}-bg)` ``), not static Tailwind utility classes — a deliberate deviation from the build brief's own example (`bg-[--color-alert-info-bg]`).** Tailwind's compiler performs static analysis of class name strings to decide which utilities to generate; a runtime-interpolated class name (`` `bg-[--color-alert-${tone}-bg]` ``) is invisible to that analysis and would simply not generate the needed CSS — the class would be present in the DOM but do nothing, a real, silent failure mode, not a style preference. Toast and Badge — the two most directly comparable existing components, both tone-driven — already established the correct pattern for this exact situation: tone-dependent colours via inline `style` with the token name template-interpolated, structural/static classes (`sr-only`, `shrink-0`) via Tailwind. Alert follows that established, working precedent instead of the brief's illustrative (and for a dynamic `tone` prop, non-functional) example.

**Token declaration: `:root` AND `.dark`, not "`:root` only" as the build brief stated.** The brief's STEP 1 said the new tint family could be "defined once in `:root`, no `.dark` override needed — both operands flip per mode." That assumption doesn't hold, for two independent reasons, and this build does NOT follow it: first, factually, `--color-status-{tone}` for success/error/warning/info is the SAME hex in both light and dark (see the Status badge fills table in `docs/DOC-colour-system.md`) — only `--color-bg-surface` actually varies by mode for these four tones, not "both operands"; second, and decisively, the 2026-07-06 Badge tint fix pass (see that entry below) empirically PROVED, with a minimal isolated repro, that a `color-mix()` custom property declared only at `:root` bakes in its `var()` inputs at `:root`'s own resolved values and does not re-substitute per descendant even when a descendant's environment (e.g. inside `.dark`) has genuinely different values for those inputs — the exact bug that made the original Badge tint render pale light-mode colours inside dark-mode Storybook canvases. Re-running that same mistake for a brand-new token family, in the same design system, one build after the fix pass that discovered and documented it at length in both `docs/DOC-colour-system.md` and `CLAUDE.md`'s Badge sizing row, would reintroduce a known, already-diagnosed, already-fixed bug. `--color-alert-{tone}-bg`/`-border` are therefore declared in BOTH `:root` and `.dark`, identical formula, identical per-tone percentages in both blocks (no tone needed a dark-only percentage adjustment the way Badge's neutral border did) — exactly Badge's now-corrected pattern, not Badge's original, buggy one.

2026-07-06 — [DESIGN-SYSTEM] Built Toast (transient/floating auto-dismissing confirmation) — Components phase — plus one new motion token, `--duration-toast`. Files: `src/components/ui/Toast/Toast.jsx` · `src/components/ui/Toast/ToastProvider.jsx` · `src/components/ui/Toast/useToast.js` · `src/components/ui/Toast/index.js`. No Storybook story in this pass (separate follow-up prompt, explicitly deferred, not silently skipped).

**Three tones only — success/error/info; warning and neutral deliberately excluded.** Toast is a one-shot confirmation of an action the owner just took; "warning" and "neutral" both describe ongoing/ambient states (a stale connection, a new/closed lead) that belong on Badge (inline label) or Alert/Banner (standing message), not on something that appears and vanishes in 5 seconds. Adding them to Toast would blur the Toast-vs-Banner line this repo already draws (see the original Alert/Banner build decision) rather than reinforce it.

**Persistence rules.** success/info auto-dismiss after `--duration-toast` (5000ms); error is unconditionally PERSISTENT (no auto-dismiss, manual dismissal only) — an error is exactly the thing a distracted, hands-dirty owner must not have silently time out unread. Any toast with an `action` is ALSO persistent regardless of tone (Carbon's rule: if there's something to do about it, it must not disappear before the owner can do it) — a plain success toast with an "Undo" action stays up until dismissed or the action is taken, same as an error.

**ARIA split, not a single convention.** success/info use `role="status"` + `aria-live="polite"` (announced without interrupting); error uses `role="alert"` + `aria-live="assertive"` (interrupts, as an error should). The live-region container (`<ol>`) is always mounted, even with zero toasts, and each `<li>` carries its own role/aria-live rather than the container declaring one globally — a single always-present live region with content inserted into it announces far more reliably across screen readers than toggling the whole region in and out, which some AT/browser combinations miss.

**Top-anchored, not bottom.** Rejected a bottom-anchored stack (common elsewhere) specifically because Quicklo's own layout already owns the bottom of the mobile viewport twice over: the bottom navigation bar (< 600px) and, on the lead-detail screen, the one-click reply box anchored at the bottom of the panel. A toast stacking at the bottom would either sit on top of the reply box the owner is actively using, or get hidden behind the bottom nav — both worse than the minor convention deviation of top-anchoring. Mobile: top-centre, full width minus `--space-4` gutters, `top: calc(var(--space-4) + env(safe-area-inset-top))`. Desktop: top-right, fixed 400px, `--space-4` from top/right plus `env(safe-area-inset-right)`.

**Hand-rolled, not Radix Toast.** This is the first imperative/queued component in the repo — every other component renders inline where it's used; a toast needs an API callable from anywhere (a save handler, a copy button) with no natural JSX slot. Built as a local queue + portal (`ToastProvider` holds state, `useToast()` exposes the imperative API) rather than adopting Radix Toast or another third-party library, for the same reason DateTimePicker's scrim/dialog is hand-rolled rather than a library dialog: this repo builds its own overlay primitives for repo-wide consistency (shared token usage, shared motion/z-index conventions, no extra dependency for one component) instead of mixing in an external implementation with its own conventions.

**`--duration-toast` (5000ms) — new motion token, deliberately excluded from the reduced-motion collapse.** Added to `globals.css`, NOT listed in the `@media (prefers-reduced-motion: reduce)` block that zeroes every other duration token. Reasoning: that block exists to strip MOTION for users who've asked for it — but `--duration-toast` isn't motion, it's a display-persistence timer (how long content stays legible on screen). Zeroing it would make success/info toasts vanish instantly for reduced-motion users specifically, which has nothing to do with their stated preference and would actively harm them (less time to read, not more). Toast's actual motion — the enter/exit slide+fade — uses `--duration-base`/`--ease-enter`/`--ease-exit` exactly like every other component, and that DOES collapse to instant as normal; only the persistence timer is exempted. The JS auto-dismiss timer reads `--duration-toast` live via `getComputedStyle` (same convention as DateTimePicker's scrim-close delay reading `--duration-slow` live) — never hardcoded — so a future token-value change or a `prefers-reduced-motion`-style future toggle on persistence itself would propagate with zero component changes.

**Title uses the type token's natural 1.5rem line-height, not the tight single-line override.** Every other component with a label (Button, Input, Badge) applies a tight explicit line-height to fix the browser's line-box-inflation vertical-centering bug, on the assumption the label is always one line. A toast title is not guaranteed to be — "Delivery failed after 3 retries — contact James M. manually" easily wraps to two lines — so applying the single-line fix here would clip or misalign wrapped text. Toast's title is the one component-label case in this repo that intentionally keeps the natural, taller line-height.

**z-index 9500 — deliberately above Tooltip's 9000.** Informal z-scale forming in this repo: Tooltip 9000, Toast 9500. A toast is a confirmation the owner needs to see and dismiss; a tooltip is disposable hint text that should never be capable of visually burying one.

**States excluded, and why.** Toast models exactly four states — `entering` · `resting` · `paused` · `exiting` — plus whatever states its composed `Button` (action) and `IconButton` (close) already carry. Explicitly NOT modelled: `disabled` (a toast is never partially interactive — it's either up or it's gone), `loading` (nothing about a toast fetches or awaits — it's shown after an action already completed), and "error as a state" (error is a TONE — a colour/urgency/timing classification chosen at creation time — not a state a toast transitions into the way a paused timer is a state; conflating the two would suggest a toast could somehow become an error after being created, which it can't).

**Zero new colour tokens.** Toast reuses `--color-bg-surface`, `--color-status-{success,error,info}`, `--color-status-{tone}-text`, `--color-text-secondary`, `--color-text-on-interactive-error` (for its literal mode-invariant white, reused on the status-circle glyph exactly as the original Badge build once used it), `--elevation-2`, `--radius-md`, `--space-*`, `--text-body-lg`/`-md`, and `--color-focus-ring` via the composed `Button`/`IconButton`. The 14px glyph size in the original spec was NOT implemented literally — `Icon.jsx`'s locked semantic scale only has `sm`(16)/`md`(20)/`lg`(24), and adding a one-off size would break that scale for a single component; `sm` (16px) is used instead, flagged in a code comment.

**Fix 4 — native `<input type="date">` typed-year bug ("types 2025, lands on 1901").** Root cause: the field was tightly CONTROLLED straight from parsed `Date` state. Per spec, a native date input's `.value` IDL attribute is `''` for ANY incomplete segmented entry — so every keystroke while typing a year (before all four digits are in) fired `onChange` with `''`, which the old code parsed (`fromISODate('') → null`) and pushed all the way up through `onChange` to the parent `DateRangePicker`, which then handed the identical `''` straight back down as the controlled `value`. Forcing the DOM's `value` back to `''` in response to the browser's own transient, incomplete-segment report is exactly the "apply a mask while typing" mistake MD3 warns against, and is what corrupted the browser's internal per-segment (year/month/day) editing state — producing the reported 1901 symptom. **Fix:** the field (`ManualDateField`, a new local subcomponent) is now genuinely **uncontrolled** — `defaultValue` plus a ref — while the user types; nothing writes to it in response to its own `onChange`. It is synced imperatively FROM external changes only (a calendar tap, a preset, the other field), via an effect keyed on the external ISO string that only ever assigns a complete date or `''`, never an intermediate one. `onChange` only propagates upward when the browser reports a complete, valid `YYYY-MM-DD` (tested with `/^\d{4}-\d{2}-\d{2}$/`); a momentary `''` mid-typing is silently ignored, not treated as "clear this field." A still-empty value is only treated as an intentional clear **on blur** (editing is done at that point, so empty means the user meant it), not on every keystroke. A fully-typed but future-dated value is rejected at the same commit point (string comparison against the `max` attribute, avoiding a second Date-parse) and the field's own display is reverted immediately, rather than left showing an accepted-looking future date that's out of sync with the actual selection. Min/max/disabled-future constraints are enforced only at this commit point, never per keystroke. Verified live: dispatching a raw `''` `input`/`change` event (simulating the exact mid-typing artifact) left the trigger showing its previous committed value unchanged (not cleared); dispatching a complete `2025-06-15` committed correctly with no snap-back, and the calendar re-rendered to "June 2025" with the 15th shown `aria-selected`. (Note: this environment's headless Chromium does not process synthetic per-keystroke segment input into native date-input widgets at all — zero `input`/`change` events fired for `pressSequentially()` — so the exact keystroke-by-keystroke path could not be replayed end-to-end here; the fix was verified via `.fill()` for the complete-value path and via direct event dispatch for the specific intermediate-value artifact the bug report described, which together exercise the same code path a real browser's segmented typing would.)
